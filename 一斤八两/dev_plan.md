# 《一斤八两》开发实施计划

## 0. 文档目的

本计划用于把《一斤八两》从概念逐步推进为一款可发行、可完成、可维护的完整游戏。它不是固定不变的日历，而是一套**以可玩版本和阶段验收为核心的决策流程**：每一阶段必须产出可检查的成果，通过验收后才能扩大投入。

本计划基于以下产品假设：

- **类型**：第三人称社会潜行 / 动作惊悚 / 叙事游戏。
- **核心体验**：观察骗局、搜集事实、操纵人物与空间条件，在短促高风险冲突发生前取得优势，并承担事件被他人如何讲述的后果。
- **目标规模**：6–8 小时主线，5 个高密度半开放街区，约 10–12 场主要冲突。
- **首发平台**：Windows PC，键鼠与手柄同时支持。
- **商业模式**：买断制单机游戏；不设计内购、赛季或强制联网。
- **目标团队**：小型独立团队，核心 5–12 人；美术、配音、音乐、测试和本地化可按阶段外包。
- **建议开发周期**：获得稳定团队与资金后约 24–36 个月。若由 1–3 人开发，应先只承诺原型和垂直切片，不应直接承诺完整规模。

所有周期与预算只能在概念验证和垂直切片完成后重新估算。未通过阶段门槛时，应缩减、重做或终止项目，而不是用更多内容掩盖核心体验问题。

## 1. 产品北极星与不可妥协原则

### 1.1 玩家应获得的核心感受

玩家完成一次优秀行动后，应能明确说出：

> “我不是靠系统给出的正确选项赢了，而是自己观察了现场、判断了人、安排了位置，让对方一步步进入了我的局。”

### 1.2 三个设计支柱

1. **先赢局，再动手**
   - 准备质量必须真实改变对话、NPC决策、冲突难度和撤离结果。
   - 战斗不是常规奖励循环，而是高风险收束、威慑手段或计划失效后的应急处理。

2. **空间和社会关系同等重要**
   - 椅子、柜台、门、灯、收音机、摩托停车方向等空间条件，应与证人、同伙、街坊声望和公开承诺一样重要。
   - NPC不能只按好感度行动，必须考虑自身利益、恐惧、立场、所见事实和周围观众。

3. **赢得事件，不等于赢得故事**
   - 系统同时记录事实、证人视角和传播后的版本。
   - 玩家可以打赢现场却失去舆论、关系、自由或后续机会。

### 1.3 明确不做的内容

- 不做可自由屠杀的城市沙盒。
- 不做依赖血条和连招的常规动作游戏。
- 不做“寻找所有高亮证据后选择金色台词”的公式化流程。
- 不做无边界、指数爆炸的任意剧情树。
- 不做多人、开放世界无缝大地图、载具战斗、随机生成主线或持续在线服务。
- 不直接使用受版权保护的电视剧人物、台词、音乐、镜头、演员肖像或可识别场景；只保留抽象设计灵感，并完成原创化与法律审查。

### 1.4 核心体验指标

开发期间所有测试围绕以下指标，而不是单纯询问“好不好玩”：

- 玩家能否说清自己为何成功或失败。
- 准备行为是否显著改变冲突，而非只改变分数。
- 玩家是否主动观察、试探和布置，而非等待任务标记。
- 非战斗解法是否紧张、有操作性、有代价。
- 暴力是否被感知为危险选择，而非最高效的默认答案。
- 不同玩家是否能产生可复述的不同事件版本。
- 玩家是否愿意立即重玩同一事件验证另一种方案。

## 2. 总体阶段与决策门

| 阶段 | 主要目标 | 建议周期 | 关键决策 |
|---|---|---:|---|
| 0. 项目立项准备 | 明确权利、团队、工具与决策机制 | 1–2 周 | 是否具备合法且可持续的开发基础 |
| 1. 概念与市场验证 | 验证受众、定位、范围与商业可行性 | 3–6 周 | 概念继续、收缩、转向或终止 |
| 2. 纸面与低成本原型 | 分别验证核心机制，不追求美术 | 6–10 周 | 核心循环是否有可操作的乐趣 |
| 3. 首个可玩原型 | 证明机制能组成完整事件 | 8–12 周 | 是否值得制作垂直切片 |
| 4. 垂直切片 | 证明最终品质、生产管线与市场表现 | 4–6 月 | 是否进入完整制作 |
| 5. 完整预制作 | 锁定范围、架构、内容模板和计划 | 2–3 月 | 预算与完整制作计划批准 |
| 6. 正式制作至 Alpha | 完成全部系统和可通关粗制内容 | 8–12 月 | 功能锁定，禁止增加核心系统 |
| 7. Alpha 至 Beta | 完成最终内容、美术、音频和叙事 | 4–8 月 | 内容锁定，只做修复与打磨 |
| 8. 打磨与发行候选版 | 稳定、优化、无障碍、本地化 | 2–4 月 | 是否达到可发行标准 |
| 9. 上线准备与发行 | 完成商店、营销、部署和首发 | 1–2 月 | Gold Master / 正式发布 |
| 10. 上线后支持 | 修复问题、维护口碑、评估扩展 | 至少 6 月 | 继续维护、扩展或结束支持 |

阶段可以局部重叠，但不能跳过决策门。任何对后续阶段影响巨大的未知项，必须先用最便宜的实验解决。

# 第一部分：立项与验证

## 阶段 0：项目立项准备

### 目标

建立项目的法律、组织和技术基础，避免在原型成功后才发现版权、所有权、资金或协作方式不可行。

### 工作内容

#### 0.1 原创化和权利边界

- 将电视剧片段视为设计研究材料，而非可直接开发的IP。
- 建立原创化清单：
  - 主角、配角、城市、组织和事件全部使用原创名称与背景。
  - 不复刻演员面貌、声音、标志性服装组合或逐字台词。
  - 不逐镜重现原场景，不使用原剧截图、录音或配乐。
  - “黑秤、公开承诺、空间卡位、预留退路”等属于抽象机制，可重新创作。
- 在公开融资、签约发行商或大规模制作前，聘请熟悉游戏与影视版权的律师进行书面审查。

#### 0.2 项目治理

- 明确以下角色，即使一人兼任也要明确职责：
  - 产品 / 创意负责人：维护产品支柱，拥有范围最终决定权。
  - 制作人：排期、预算、风险、外包和阶段门。
  - 技术负责人：架构、工具、性能和构建质量。
  - 设计负责人：核心循环、关卡、叙事系统与平衡。
  - 美术负责人：视觉标准和资产验收。
- 规定争议解决方式：设计争论优先通过可玩测试和指标裁决，而非资历或个人偏好。
- 建立每两周一次可玩版本评审；不接受只展示文档、概念图或口头进度。

#### 0.3 基础工具

- 版本控制：代码和小型资源使用 Git；大型二进制资源启用 Git LFS。若团队和资产规模明显扩大，再评估 Perforce。
- 任务管理：建立可追溯的功能、内容、缺陷和风险列表。
- 文档：建立单一事实来源，至少包括产品简述、GDD、TDD、视觉圣经、音频指南、叙事资料库和测试记录。
- 构建：从第一个引擎原型开始支持一键生成可分发构建，不允许项目长期只能在开发者编辑器中运行。

### 产出物

- 项目章程与角色责任表。
- 原创化 / 版权风险清单。
- 初始预算类别和资金上限。
- 版本控制仓库、任务系统、文档目录和构建命名规则。
- 风险登记表，包含负责人、触发信号和缓解方案。

### 验收标准

- [ ] 所有核心贡献者的成果所有权、署名、报酬和退出条款有书面协议。
- [ ] 项目不依赖取得《征服》或“刘华强”相关授权才能成立。
- [ ] 任意团队成员可以从干净环境拉取项目并运行当前构建。
- [ ] 每项高风险问题都有负责人和下一次检查时间。
- [ ] 创意负责人能用一分钟解释“本作是什么、不是什​​么、为何值得做”。

## 阶段 1：概念、受众与商业验证

### 目标

确认产品定位足够清晰、存在可触达的目标玩家，并把完整游戏范围压缩到小团队可以完成的程度。

### 工作内容

#### 1.1 编写一页产品提案

一页提案必须回答：

- 玩家是谁、在做什么、为什么这些行为有趣。
- 三个设计支柱和一个最强差异点。
- 目标玩家：偏好叙事潜行、沉浸模拟、犯罪惊悚、短篇高重玩游戏的PC玩家。
- 6–8小时产品为何值得购买，而不是只作为免费短片体验。
- 首发语言、平台、价格区间和最低销量假设。

#### 1.2 竞品与相邻产品研究

研究不应只寻找完全相同的游戏，而应拆分能力来源：

- 社会潜行和身份压力。
- 沉浸模拟式空间解法。
- 高风险短促战斗。
- 多视角证词或事件重构。
- 小型高密度叙事街区。

对每个参考产品记录：

- 玩家最常称赞的体验。
- 1–2星评价中的重复痛点。
- 制作规模和内容密度。
- 商店标签、售价、评论量和可见度来源。
- 本作可以借鉴的原则，以及必须避免的表面模仿。

#### 1.3 用户访谈和概念测试

- 招募至少 20 名目标玩家，不以亲友为主。
- 先展示不超过一页的文字与少量原创概念图，避免用长篇解释诱导答案。
- 让受访者用自己的话复述玩法，记录误解。
- 测试至少三种对外表达：
  1. “先赢局，再动手”的社会潜行游戏。
  2. “每场冲突前十分钟决定之后十秒”的惊悚游戏。
  3. “事实、证人和流言共同改写剧情”的犯罪叙事游戏。
- 不询问“你会不会买”作为主要证据；要求玩家排序兴趣点、指出疑虑，并与其他真实游戏比较。

#### 1.4 范围和财务模型

- 分别建立最小版、目标版和扩展版：
  - **最小版**：3个街区、4–5小时、6–8场主冲突。
  - **目标版**：5个街区、6–8小时、10–12场主冲突。
  - **扩展版**：只能在目标版资金和进度稳定后考虑。
- 估算人月、外包、软硬件、配音、本地化、法务、营销、平台分成、税费和至少 20% 应急储备。
- 明确最低可持续销量，而不是用理想销量反推预算。

### 产出物

- 一页产品提案。
- 竞品和市场差异报告。
- 目标玩家画像与访谈记录。
- 最小版 / 目标版范围表。
- 初始预算、现金流、售价和回本敏感性模型。
- 更新后的十大风险清单。

### 验收标准

- [ ] 至少 70% 的目标受访者无需额外解释即可正确复述核心玩法。
- [ ] “准备改变结果”进入目标玩家最感兴趣的前三项。
- [ ] 至少一半目标受访者表达“愿意试玩”，并能给出具体原因。
- [ ] 团队能指出本作与相邻竞品的系统差异，而非只依赖中国题材。
- [ ] 目标版范围在人力、资金和时间上有明确可行路径。
- [ ] 如果去掉影视梗来源，产品提案仍然成立。

### 未通过时的处理

- 玩家只对网络梗感兴趣：停止完整游戏计划，考虑制作小型独立短作。
- 玩家喜欢故事但无法理解玩法：重写核心循环并先做交互原型。
- 目标范围无法融资或自筹：降至最小版，不得假设未来自然获得更多资源。

## 阶段 2：纸面原型与风险拆解

### 目标

以最低成本分别验证四个核心系统：压力对话、空间预演、短促冲突、现场叙事。此阶段不制作正式美术。

### 2.1 建立“瓜摊事件”状态模型

先用卡片、表格或简单网页模拟事件。状态至少包括：

- **事实状态**：是否有磁铁、瓜是否成熟、谁先拿武器、谁移动了物件。
- **认知状态**：每名NPC看见、听见、怀疑和误解了什么。
- **社会状态**：老板自信、警觉、羞耻、同伙忠诚、围观压力。
- **空间状态**：入口、阻挡物、武器位置、人物可达路径和撤离路线。
- **叙事状态**：街坊版本、警方版本、敌对势力版本的证据来源。

所有状态必须能被设计师检查。禁止将关键结果埋在不可解释的随机值中。

### 2.2 压力对话纸面测试

- 对话选项以“意图”组织：试探、附和、质疑、逼诺、退让、转移话题。
- 每个意图根据玩家已掌握事实、说话地点、听众和目标心理产生不同结果。
- 测试玩家能否：
  - 在不看数值的情况下理解对方正在警觉或失去支持。
  - 通过前序安排让同一句话获得新意义。
  - 接受没有“完美选项”的不确定性。
- 避免隐藏作者答案：失败后必须能指出可观察的原因。

### 2.3 空间预演桌面测试

- 使用俯视地图、人物棋子和物件卡模拟瓜摊。
- 玩家拥有有限观察时间和有限预演槽位。
- 允许玩家改变少量物件位置，但每次动作都有被看见或引起怀疑的风险。
- 验证空间准备是否至少能改变：
  - 同时接近玩家的人数。
  - 冲突开始距离。
  - 可用逃生路线。
  - 证人能看到的内容。

### 2.4 现场叙事规则测试

- 将“客观发生的事”与“每个人能证明的事”分开。
- 用规则生成简短事件摘要，并要求玩家指出为何产生该版本。
- 规则必须确定性优先；随机传播只能用于不关键的修饰。
- 测试结果应产生后续玩法影响，例如店家是否提供情报、警方巡逻是否加强、对手是否改变站位。

### 2.5 战斗边界测试

- 用极简输入模拟推、挡、抓、缴械、威慑、逃跑，不设计长连招。
- 一次冲突控制在 5–20 秒。
- 玩家受伤和造成严重伤害都必须有后续代价。
- 测试“非致命控制”和“撤离”是否比击倒所有敌人更常成为理性目标。

### 产出物

- 可重复运行的瓜摊事件纸面原型。
- 状态变量字典和事件因果图。
- 每个核心系统至少两个被否决的方案及原因。
- 15–20名外部测试者的观察记录。
- 更新后的核心循环说明。

### 验收标准

- [ ] 至少 60% 的测试者会主动重玩事件尝试不同安排。
- [ ] 至少 70% 的测试者能解释一个成功或失败的因果链。
- [ ] 不阅读说明书的测试者能理解至少三种对话意图的差别。
- [ ] 空间调整能产生可感知的玩法差异，而非只改变动画。
- [ ] 至少存在三类有效结果：公开压服 / 安全撤离、受控冲突、严重失控。
- [ ] 暴力不是多数玩家在信息充分时唯一或明显最优的选择。

# 第二部分：原型与垂直切片

## 阶段 3：首个引擎可玩原型

### 目标

用灰盒和占位资源证明四个系统可以组合成一段完整、可理解、有节奏的 20–30 分钟体验。

### 3.1 引擎和技术方向决策

在制作前用 1–2 周技术试验比较候选引擎，依据以下项目评分：

- 第三人称角色、AI导航、动画状态机和对话工具成熟度。
- 小团队开发效率和成员经验。
- PC构建、手柄、存档、分析和本地化支持。
- 场景流送、光照、性能诊断和外包资源兼容性。
- 授权费用和长期维护风险。

选择后记录决策理由。除非出现阻断性问题，不在项目中期换引擎。

### 3.2 原型范围

只制作一条灰盒街道、瓜摊、修车铺和两条撤离路线。包含：

1. 到达并选择停车朝向。
2. 自由观察环境。
3. 与老板、同伙、路人进行压力对话。
4. 找出或错过黑秤证据。
5. 移动一件关键物件改变通路。
6. 进入至少三种冲突结果。
7. 撤离。
8. 显示街坊和警方对事件的不同描述。

### 3.3 技术原型模块

- 第三人称移动、交互、相机和基础手柄操作。
- NPC感知：视线、听觉、注意目标和可疑度。
- 对话状态机：意图、条件、公开承诺和中断。
- 事实 / 认知 / 证词数据模型。
- 可移动物件和导航更新。
- 短促冲突状态机。
- 检查点、保存 / 读取和事件复盘。
- 调试界面：可查看任意NPC知道什么、为何做出当前决定。

### 3.4 原型设计规则

- 不制作正式角色、过场动画、精细材质或完整配音。
- 不用UI直接标出所有答案；仅提供玩家角色合理可感知的信息。
- 每次测试只改变一个主要变量，保留版本和结果。
- 原型允许难看，但不允许因输入迟钝、镜头失控或严重Bug污染测试。

### 3.5 外部盲测

- 至少 20 名目标玩家，每人第一次游玩前只看商店式简介和基础操作。
- 研究者不在旁提示；记录玩家视线、停顿、行动顺序和复盘解释。
- 测试后询问：
  - 你认为目标是什么？
  - 哪些准备真实帮助了你？
  - 冲突为何发生？
  - 如果重玩，你会改变什么？
  - 哪一刻最紧张，哪一段最无聊？

### 产出物

- 可独立运行的 Windows 灰盒构建。
- 原型设计说明与状态调试工具。
- 自动构建和最小烟雾测试。
- 测试录像、行为记录和问题优先级。
- 核心系统保留 / 重做 / 删除决定。

### 验收标准

- [ ] 新玩家在不受指导的情况下完成一轮事件的比例不低于 80%。
- [ ] 首轮体验中至少 70% 玩家主动使用两种以上准备手段。
- [ ] 至少 60% 玩家愿意立刻重玩，并实际选择不同策略。
- [ ] 多数玩家能正确解释准备如何影响冲突或证词。
- [ ] 从开始对峙到结果形成的节奏没有连续超过 3 分钟的无意义等待。
- [ ] 非战斗成功路线具有明确操作、风险和紧张感。
- [ ] 调试工具能解释NPC关键决策，不出现无法追踪的“AI突然发疯”。
- [ ] 低端目标PC保持稳定可玩，不存在架构级性能阻塞。

### 原型决策门

- **通过**：进入垂直切片。
- **有条件通过**：只允许针对一个明确薄弱系统再进行最多两轮原型迭代。
- **不通过**：缩小为短篇实验游戏，或停止项目。不得以添加剧情和美术替代核心乐趣。

---

## 阶段 4：垂直切片

### 目标

制作一段接近最终品质的完整章节，证明三件事：

1. 游戏核心确实有趣。
2. 团队能以可承受成本生产这种内容。
3. 玩家和市场能理解并记住它的差异点。

### 4.1 垂直切片内容

建议将“第一章：一块磁铁”制作成 25–40 分钟体验，包括：

- 原创开场与动机，不复刻影视剧情。
- 可骑乘或短距离操控摩托抵达；若载具成本过高，可改为交互式到达和停车决策。
- 街区自由踩点。
- 一项核心骗局、三项关键事实、两处决定性站位。
- 5–7 名有不同立场的NPC。
- 至少三条主要解决路径：
  - 证据与公众压力形成不战而胜。
  - 有限、可控的近身冲突后撤离。
  - 计划失控并产生严重后果，但剧情仍可继续。
- 街坊版与警方版事件复盘。
- 一个会在后续章节产生影响的结果钩子。

### 4.2 最终品质基线

- 一套接近最终效果的街区模块化美术。
- 一名主角、主要NPC和人群的代表性角色品质。
- 最终方向的动画、表情、镜头、灯光、环境音和UI。
- 中文完整配音或足以评估表演方向的代表性配音。
- 基础无障碍：字幕、字号、音量分类、按键重映射、色彩不作为唯一信息。
- 可靠的存档、暂停、失败恢复和设置菜单。

### 4.3 生产管线验证

记录每类资产和内容的真实制作时间：

- 一个模块化店面。
- 一名主要NPC和一名复用型NPC。
- 一段分支对话。
- 一个完整事件状态图。
- 一套冲突动画。
- 一分钟配音从脚本到游戏集成。

根据实测速度重新估算完整游戏。不得继续使用概念阶段的乐观估算。

### 4.4 技术质量

- 每次主分支合并自动生成构建。
- 自动检查关键资源缺失、对话断链、无出口状态和存档序列化。
- 建立性能预算：CPU、GPU、内存、显存、NPC数量、音频声部和加载时间。
- 建立崩溃报告和匿名分析事件；测试版本必须允许玩家主动拒绝数据收集。

### 4.5 市场测试

- 用实际玩法剪辑制作 30–60 秒概念预告，不用纯CG掩盖玩法。
- 建立匿名商店页文案或广告素材测试，比较不同USP。
- 进行至少 30–50 名目标玩家盲测，其中大部分未参加过前期测试。
- 如果条件允许，在活动或线上提供公开试玩并观察：
  - 点击到试玩意愿。
  - 试玩完成率。
  - 愿望单或关注转化。
  - 玩家复述的核心卖点。

### 产出物

- 接近最终品质的独立垂直切片构建。
- 更新后的 GDD、TDD、视觉圣经和音频指南。
- 完整内容生产成本报告。
- 完整游戏预算、人员、排期和现金流预测。
- 市场测试结果和定位建议。
- 全项目风险及缓解方案。

### 验收标准

- [ ] 至少 80% 的目标玩家完成切片。
- [ ] 中位游玩时间处于设计目标范围，不依赖卡关拉长。
- [ ] 至少 70% 玩家能复述“通过准备控制冲突”的核心体验。
- [ ] 至少 50% 玩家在结束后主动重玩或明确表示想尝试另一方案。
- [ ] 玩家策略分布不被单一最优路线垄断；任一路线不应超过约 60%。
- [ ] 非暴力路线的紧张度和满意度不显著低于暴力路线。
- [ ] 关键失败均能从可感知线索解释。
- [ ] 在最低目标硬件上达到锁定的帧率、内存和加载指标。
- [ ] 内容生产速度支持在批准预算与周期内完成目标版。
- [ ] 宣传素材能让陌生玩家正确理解它不是常规格斗或纯对话游戏。

### 垂直切片决策门

只有以下条件同时满足才进入完整制作：

- 核心体验指标通过。
- 完整预算已有资金来源或可信融资路径。
- 内容生产速度经实测可行。
- 团队关键岗位已落实。
- 法务判断原创化程度可接受。

若乐趣通过但生产成本过高，应减少街区、角色和分支数量；若市场表达不清，应调整定位；若核心乐趣未通过，应停止扩大投入。

# 第三部分：完整预制作与正式制作

## 阶段 5：完整预制作

### 目标

把垂直切片中验证过的做法转化为可重复的内容模板，并在大规模制作前锁定范围、架构和质量标准。

### 5.1 完整 GDD

GDD至少包含：

- 核心循环、玩家能力、输入和反馈。
- 压力对话规则及状态变化。
- NPC认知、立场、恐惧、忠诚和公开压力模型。
- 空间预演、可动物件、路径和风险规则。
- 冲突、伤势、威慑、缴械、逃跑和死亡边界。
- 事实、证词、流言及后续影响模型。
- 成长系统：增加判断能力，不升级为超人战斗力。
- 摩托系统的最终范围。
- UI、教程、难度和无障碍方案。
- 存档、检查点、重玩和二周目规则。
- MVP、可删减项和发行后候选项。

### 5.2 章节与事件设计

每个主要事件使用统一模板：

1. 玩家可见目标与隐藏矛盾。
2. 一项核心骗局或利益冲突。
3. 三项关键事实，分别通过不同手段验证。
4. 两处决定性空间条件。
5. 3–5 名关键NPC及各自利益。
6. 至少三类结果，不要求每类都有大量独立剧情。
7. 事件对街区、警方、关系和后续任务的影响。
8. 可删减边界和最坏情况下的线性保底版本。

五章应形成机制递进：

- 第一章教会玩家读懂事实、承诺和卡位。
- 第二章引入视线误导、镜面、停电或录音证据。
- 第三章扩大空间和潜入比重，验证工业设施中的尺度变化。
- 第四章让敌人主动消除证人，迫使玩家制造公共现场。
- 第五章同时处理人群安全、证据传播和目标逃亡，综合所有系统。

### 5.3 技术设计

- 采用数据驱动事件定义，避免每个任务编写无法复用的硬编码逻辑。
- 事实、认知、证词三个层次必须拥有清晰数据边界。
- NPC决策需提供设计师可读的原因日志。
- 对话工具支持条件预览、断链检查、演出标记和本地化导出。
- 关卡工具支持查看导航、视线、声音传播、证人覆盖和可动物件状态。
- 保存系统从一开始支持版本迁移和损坏检测。
- 自动测试覆盖关键状态转换、存档往返和章节完成路径。

### 5.4 美术与音频规范

- 视觉圣经定义年代、地域、色彩、材质、招牌、服装和污染程度。
- 建立模块化街区套件，优先复用建筑结构，通过店面、招牌、灯光和陈设形成差异。
- 规定角色层级：主角 / 主要NPC / 次要NPC / 人群，各自拥有不同面数、材质、动画和表情预算。
- 音频以环境压迫和信息传递为核心；冲突不使用英雄化音乐。
- 方言只作为人物特征，不应阻碍理解；所有关键语音提供准确字幕。

### 5.5 内容与范围锁定

- 建立逐章资产清单、脚本字数、配音分钟数、动画数量和事件状态数量。
- 给每项内容标记：
  - 必须有。
  - 可以简化。
  - 可以删除。
- 控制分支：分支优先改变状态、资源、关系和后续条件，而不是无限制造独立关卡。
- 任一主要事件的关键状态组合必须可被测试覆盖；无法覆盖的复杂度必须削减。

### 产出物

- 批准版 GDD、TDD、视觉圣经、音频指南和叙事圣经。
- 五章节拍表、任务清单和依赖图。
- 资产、动画、配音和本地化总表。
- 2周冲刺计划、里程碑和人员计划。
- 测试策略、性能预算和硬件矩阵。
- 最终预算与范围基线。

### 验收标准

- [ ] 每项核心功能在GDD和TDD中都有一致定义。
- [ ] 每章都能指出新增机制、复用机制和制作成本。
- [ ] 所有关键内容有明确负责人、依赖和完成定义。
- [ ] 目标版总量不超过垂直切片实测产能推算的 80%，保留缓冲。
- [ ] 所有章节都有可删减方案，删减后主线仍完整。
- [ ] 事件复杂度可由自动测试、路径测试和人工测试共同覆盖。
- [ ] Alpha、Beta、RC日期和资金节点相互匹配。

---

## 阶段 6：正式制作至 Alpha

### 目标

实现所有发行必需功能，并使完整游戏从头到尾可通关。Alpha阶段允许粗糙资源和占位演出，但不允许缺失核心系统或主线章节。

### 6.1 制作节奏

- 使用固定两周冲刺。
- 每个冲刺必须交付可玩的主线构建。
- 冲刺开始确定单一体验目标，结束进行跨职能试玩，而非分别汇报代码、美术和脚本。
- 每四个冲刺检查一次范围、预算、人员健康和内容吞吐量。
- 主分支持续可玩；大型功能使用短生命周期分支，合并前必须评审。

### 6.2 并行工作流

#### 工程

- 完成所有核心系统、工具、存档、设置、输入、分析和崩溃报告。
- 每次合并运行编译、数据校验和关键路径自动测试。
- 每周至少一次在最低配置硬件上分析性能。
- 不用“以后优化”接受明显超出预算的系统设计。

#### 关卡与系统设计

- 先灰盒整章，再加入脚本，再加入最终资产。
- 每个事件先验证信息、空间和结果，再做演出。
- 每周检查是否出现单一最优解或无意义步骤。
- 每个失败状态提供恢复、继续或清晰重试点。

#### 叙事

- 先锁章节功能和状态变化，再写最终台词。
- 剧本必须标记说话意图、潜台词、可中断点、听众和状态条件。
- 主角不被塑造成无条件正确的私刑英雄；暴力后果贯穿后续章节。
- 定期进行桌读，检查口语自然度、年代感和信息重复。

#### 美术与动画

- 环境按模块化套件生产：概念 → 灰盒匹配 → 模型 → 材质 → 碰撞 / LOD → 引擎验证 → 灯光。
- 角色按层级预算生产，避免所有路人使用主角级成本。
- 优先制作高频交互动画：观察、靠近、移动物件、威慑、推挡、缴械、受伤和撤离。
- 使用动作匹配或复杂程序动画前必须证明其维护成本合理；小团队优先可靠的有限动作集。

#### 音频与配音

- 灰盒阶段即加入占位对白和环境声，验证信息能否被听见。
- 最终录音前冻结对白，避免昂贵返录。
- 每个街区建立环境声层级、室内外过渡和关键信息声。

#### QA

- 每日构建烟雾测试。
- 缺陷级别：
  - P0：崩溃、存档损坏、无法通关。
  - P1：核心系统失效、严重状态错误、重要内容阻断。
  - P2：明显体验或表现问题。
  - P3：轻微视觉和文本问题。
- 每周缺陷分诊，P0立即处理，P1不得跨越里程碑积压。
- 建立每个主要事件的事实组合、NPC认知和结果路径测试矩阵。

### 6.3 持续玩家测试

- 每月至少一次外部盲测。
- 每季度进行一次从头开始的新玩家长测。
- 重点记录：
  - 每场事件准备时间与冲突时间。
  - 证据发现率。
  - 各结果路径选择率。
  - 死亡、重试、读档和放弃位置。
  - 玩家对因果关系的理解。
  - 章节结束后的情绪和重玩意愿。

### Alpha 产出物

- 从新游戏到结局可完整通关的构建。
- 所有MVP系统功能完成。
- 五个街区和所有主线事件至少为可玩灰盒 / 粗制状态。
- 所有关键剧情已实现，允许使用占位配音和部分占位动画。
- 完整存档、设置、输入和章节选择 / 测试工具。
- 更新后的缺陷库、性能报告和删减建议。

### Alpha 验收标准

- [ ] 完整游戏至少连续通关三次，无P0问题。
- [ ] 所有发行必需功能已存在；Alpha后禁止增加新的核心系统。
- [ ] 所有主线事件至少有三类有效结果或经批准的等价结构。
- [ ] 任意关键状态可由调试工具重现和检查。
- [ ] 最低配置机器可完整通关，性能问题已有量化清单。
- [ ] 全流程时长进入 5–10 小时可控范围。
- [ ] 最新外测中，多数玩家仍能正确理解核心循环。
- [ ] 剩余内容可以在现有人员、预算和Beta日期前完成。

### Alpha后的硬规则

- 锁定功能范围。
- 新想法进入发行后候选列表，不直接加入当前版本。
- 若进度不足，先删减独立内容，不降低核心系统清晰度、存档可靠性或无障碍标准。

---

## 阶段 7：Alpha 至 Beta

### 目标

把功能完整的粗制游戏变成内容完整的最终作品。Beta时所有正式美术、音频、文本、配音和结局均已进入游戏，之后只允许修复、平衡和打磨。

### 7.1 内容完成

- 替换所有玩家可见的占位资产和占位对白。
- 完成最终灯光、天气 / 时间氛围和场景陈设。
- 完成角色表情、关键交互和过场演出。
- 完成全部配音、音效、音乐和混音初版。
- 完成教程、日志、复盘、设置、制作人员名单和法律信息。
- 锁定所有文本后导出本地化。

### 7.2 系统调优

- 调整NPC警觉、证人可信度、同伙忠诚和舆论传播阈值。
- 消除“万能解法”和所有事件重复使用同一套路的问题。
- 确保成长能力扩大判断空间，不让玩家后期绕过全部观察。
- 调整伤势跨章影响，避免一次早期失败导致长时间无法恢复的恶性循环。
- 检查不同结局是否来自累积行为，而非最后一个二选一按钮。

### 7.3 大规模外部测试

- 招募至少 100 名符合目标画像的测试者；团队资源不足时可分多批完成。
- 测试首轮完整通关、章节重玩、不同硬件、键鼠和手柄。
- 收集匿名遥测和结构化问卷，同时保留访谈以解释数据。
- 特别检查：
  - 玩家是否因不知道“能做什么”而放弃。
  - 玩家是否把战斗误认为主要玩法。
  - 事件复盘是否帮助理解，而非替玩家判定道德。
  - 中国语境是否对海外玩家造成必要信息缺失。

### 7.4 商店与营销同步

- 上线正式商店页和愿望单活动。
- 宣传重点固定为真实玩法：
  - 社会潜行和压力对话。
  - 空间预演。
  - 事实 / 证词 / 流言。
  - 短促致命冲突。
  - 90年代末北方工业城氛围。
- 预告片不得把游戏剪成持续打斗作品。
- 发布公开试玩版时，内容应来自垂直切片或独立序章，存档和数据结构需与正式版隔离。

### Beta 产出物

- 内容完整、可从头到尾游玩的正式资源构建。
- 所有首发语言文本已集成。
- 完整配音和音频。
- 完整硬件、输入、分辨率和显示模式测试矩阵。
- 性能、崩溃、存档与路径覆盖报告。
- 商店页、预告片、截图和媒体资料包。

### Beta 验收标准

- [ ] 无占位文本、占位美术、临时音频或未完成主线内容。
- [ ] 所有结局和主要结果路径均可正常完成。
- [ ] 无已知存档损坏，旧版本存档迁移方案明确。
- [ ] P0为零；P1数量处于可在打磨期清零的范围。
- [ ] 最低配置达到既定性能目标，高频卡顿有明确修复计划。
- [ ] 键鼠和手柄均可完整操作，不依赖鼠标点击隐藏功能。
- [ ] 字幕、字号、按键重映射和关键无障碍功能完整。
- [ ] 完整外测显示核心体验、节奏和难度达到目标。
- [ ] Beta后不再新增剧情、地图、角色或核心机制。

# 第四部分：打磨、发行与维护

## 阶段 8：打磨、稳定与发行候选版

### 目标

清除阻断问题，改善最影响体验的粗糙点，使游戏在目标硬件和语言环境中稳定、清晰、一致。

### 8.1 打磨优先级

按以下顺序处理，不以“看起来更漂亮”优先：

1. 崩溃、存档、进度阻断和状态错误。
2. 玩家无法理解的目标、反馈和因果。
3. 输入、相机、碰撞、AI和冲突可靠性。
4. 性能、加载和内存。
5. 无障碍和本地化。
6. 动画、灯光、音频和视觉一致性。
7. 纯装饰性细节。

### 8.2 全流程体验检查

- 检查每章开场、事件节奏、余波和章节间过渡。
- 删除重复解释、重复操作和不能改变结果的伪交互。
- 确保重要线索通过至少两种合理渠道获得，但不自动标出答案。
- 检查玩家错过关键证据时仍能继续，只是承担不同风险。
- 检查复盘文本准确反映事实与证人视角，不泄露NPC不可能知道的信息。

### 8.3 性能和稳定性

- 对最低、推荐和高端配置进行全程采样。
- 处理着色器卡顿、资源流送峰值、内存泄漏和NPC密集区域帧时间。
- 连续运行、频繁读档、章节往返和异常退出恢复压力测试。
- 对所有支持分辨率、窗口模式、刷新率和显示器切换进行验证。

### 8.4 无障碍和本地化

- 字幕包括说话者、环境关键语音和必要音效提示。
- 支持字幕大小、背景、对比度和显示时长选项。
- 所有操作可重映射；长按、连按和快速反应提供可调选项。
- 颜色不作为唯一信息渠道。
- 测试文本溢出、断行、字体缺字、语音字幕不同步和文化语境。

### 8.5 发行候选版纪律

- 主分支锁定，仅允许经批准的缺陷修复。
- 每个修复包含复现步骤、影响范围和回归测试。
- 每个RC都完整归档代码版本、数据版本、构建工具和符号文件。
- 不在RC阶段顺手加入功能或重写稳定系统。

### RC 验收标准

- [ ] P0和P1均为零。
- [ ] P2仅保留有书面接受理由且不影响核心体验的问题。
- [ ] 完整游戏在所有目标硬件层级通过回归测试。
- [ ] 新游戏、升级存档、多个存档槽、云存档冲突和异常退出均安全。
- [ ] 所有首发语言通过语言QA。
- [ ] 无障碍清单全部通过或明确披露限制。
- [ ] 商店功能、成就、覆盖层、手柄和离线模式正常。
- [ ] 法律文本、版权、第三方许可和年龄分级资料完成。
- [ ] 候选构建可由干净环境重复生成。

## 阶段 9：上线准备与正式发行

### 目标

以可控方式发布游戏，确保玩家购买、下载、启动、游玩、反馈和退款相关流程均已准备。

### 9.1 商店与传播

- 商店描述第一屏直接解释真实玩法，不依赖“类某某游戏”。
- 截图覆盖观察、对话、空间布置、短促冲突和事件复盘。
- 预告片前 15 秒展示玩家行动如何改变局势。
- 明确游戏长度、单机属性、语言、手柄和配置需求。
- 媒体包包含玩法说明、原创世界观、团队介绍和可安全使用的素材。

### 9.2 发行演练

- 用与正式发行相同的渠道进行私密分支部署。
- 测试全新账户购买 / 激活、下载、首次启动、更新、卸载和重装。
- 验证崩溃报告、匿名分析、客服邮箱、社区渠道和隐私设置。
- 准备首发值班表和问题升级规则。
- 预先定义热修复条件：启动失败、存档损坏、广泛崩溃、主线阻断和严重安全问题。

### 9.3 评测与试玩

- 向媒体和创作者提供与正式版一致的评测构建。
- 不要求创作者把游戏宣传成动作爽游。
- 提供玩法入门资料，但不提供隐藏“正确答案”。
- 对剧透内容划定合理建议，而非限制真实评价。

### Gold Master 验收标准

- [ ] RC在目标平台完成所有内部和平台要求。
- [ ] 最终构建、调试符号、源代码标签和依赖已不可变归档。
- [ ] 商店页、价格、地区、语言、配置和发行时间全部核对。
- [ ] 首发补丁经过与主版本同等回归测试。
- [ ] 客服、社区、崩溃监控和热修复流程已演练。
- [ ] 团队明确上线后72小时和首月的响应责任。

## 阶段 10：上线后支持

### 目标

快速处理影响玩家信任的问题，以真实数据改善产品，并在不损害团队健康的前提下决定长期支持范围。

### 10.1 首发72小时

- 监控启动成功率、崩溃率、存档错误、主线阻断和退款原因。
- 将社区报告与遥测交叉验证，不以高声量个案替代数据，也不以数据否定玩家叙述。
- P0立即处理；P1形成明确公告和预计修复窗口。
- 不发布未经完整回归的仓促热修复。

### 10.2 首月

- 每周汇总技术问题、体验问题和传播误解。
- 重点观察：
  - 玩家在哪些事件放弃。
  - 暴力路线是否成为事实上的最优路线。
  - 玩家是否理解现场叙事。
  - 哪些不同解法最常被分享。
  - 商店评价是否准确描述产品。
- 优先做修复和高价值QoL，不因少数呼声立即加入大型功能。

### 10.3 中期维护

- 采用 2–4 周补丁节奏，紧急问题除外。
- 每个补丁保留兼容存档，发布清晰说明。
- 在销量、口碑、团队产能和玩家需求均支持时，才评估：
  - 新事件或短篇章节。
  - 导演评论 / 开发者模式。
  - 新语言。
  - 主机移植。
- 新内容使用缩小版概念 → 原型 → 制作 → 测试流程，不直接堆入正式版。

### 10.4 项目复盘

发行后 1 个月和 6 个月分别复盘：

- 哪些核心假设被验证或推翻。
- 实际内容成本与垂直切片预测的偏差。
- 最大返工来源。
- 玩家真正传播的卖点。
- 技术债、工具和流程问题。
- 团队工作强度和健康状况。
- 是否继续扩展、只维护，或正式结束支持。

### 上线后验收标准

- [ ] 无未处理的广泛P0 / P1问题。
- [ ] 补丁有回归测试、版本记录和存档兼容验证。
- [ ] 玩家反馈已按频率、严重度和产品支柱分类。
- [ ] 扩展内容决策基于销量、留存、口碑和产能，而非单一社区热帖。
- [ ] 项目经验被记录并转化为下一项目可复用的规则。

# 第五部分：跨阶段执行规范

## 3. 团队配置建议

### 原型期最低配置

- 1 名创意 / 系统设计。
- 1 名玩法工程。
- 1 名兼任关卡与技术美术的综合成员。
- 按需外包概念图、声音和测试。

### 垂直切片及完整制作核心配置

- 制作人 / 项目经理。
- 创意 / 游戏设计负责人。
- 2–3 名工程师：玩法、AI / 工具、引擎 / 构建可按能力兼任。
- 1–2 名关卡 / 任务设计师。
- 2–4 名美术：环境、角色、动画、技术美术可混合内部与外包。
- 叙事设计 / 编剧。
- 音频设计；配音和音乐可外包。
- 嵌入式QA或稳定合作测试团队。

若实际团队少于该规模，优先减少街区和角色，不应让核心成员长期以不可持续加班弥补范围差距。

## 4. 每项功能的完成定义

一项功能只有满足以下条件才能标记完成：

- 设计规则和边界已记录。
- 在正常游戏路径中可使用。
- 输入、相机、音频、视觉和UI反馈完整。
- 支持键鼠和手柄。
- 支持保存 / 读取。
- 有调试或诊断方式。
- 关键逻辑有自动测试，主要体验有人工测试。
- 在目标硬件性能预算内。
- 无障碍和本地化需求已考虑。
- 已进入可分发构建并通过代码 / 内容评审。

“代码写完”“资产导入”或“在设计师电脑上能跑”均不等于完成。

## 5. 每个事件的完成定义

- 玩家目标和风险可理解。
- 事实、认知和证词状态完整。
- 至少存在计划充分、计划一般和严重失控三类结果。
- 关键结果不是由不可见随机数单独决定。
- 非战斗路线具有实际操作和风险。
- 错过证据不会造成无提示死局。
- NPC决策能通过调试工具解释。
- 所有关键路径完成过人工和自动测试。
- 事件影响正确传入后续章节。
- 配音、字幕、动画、音效和复盘文本均已集成。
- 已进行至少一次未接触该事件的外部玩家盲测。

## 6. 数据与玩家测试规范

- 测试者不得只来自团队、朋友或核心粉丝。
- 记录行为优先于主观评分。
- 不在玩家卡住时立即解释；先观察他们尝试了什么。
- 区分“玩家没理解设计”和“玩家理解但不喜欢设计”。
- 所有遥测遵循最小收集、知情说明、可拒绝和安全存储原则。
- 指标用于发现问题，不用于强迫游戏变得平均化；少见但有意义的策略应保留。

## 7. 核心分析事件

建议仅记录必要的匿名事件：

- 章节 / 事件开始、完成、退出和重试。
- 发现、验证和公开关键事实。
- 对话意图及结果，不记录自由输入。
- 关键物件移动和空间变化。
- 冲突触发原因、持续时间、伤势和撤离方式。
- 各证词版本和后续结果。
- 设置、输入设备、性能和崩溃信息。

开发版应提供可视化时间线，重放一次事件的关键状态变化。

## 8. 风险登记表初始项

| 风险 | 早期信号 | 缓解措施 |
|---|---|---|
| 对话退化为找正确选项 | 玩家频繁读档试答案 | 强化可观察线索、意图反馈和多种可接受结果 |
| 空间预演只是高亮提示 | 玩家不主动观察环境 | 限制信息来源，让真实布局改变NPC可达性和证人视角 |
| AI行为不可理解 | 玩家认为失败随机 | 确定性核心规则、原因日志、减少隐藏变量 |
| 暴力成为最优解 | 多数玩家直接开打 | 强化伤势、证词、警方和关系后果，提升非暴力操作深度 |
| 内容组合指数爆炸 | 单事件测试矩阵失控 | 每关限制核心事实、决定性站位和关键NPC，复用结果框架 |
| 五章玩法重复 | 每关均为找证据后揭穿 | 每章改变信息环境、公共性、空间尺度和对手反制 |
| 题材依赖影视梗 | 玩家只讨论原场面 | 加强原创人物、主题和独立事件，法律与用户测试双重检查 |
| 时代美术成本过高 | 独特资产数量持续增长 | 模块化街区、角色层级和严格资产预算 |
| 摩托系统吞噬资源 | 载具Bug与关卡要求扩张 | 垂直切片验证；必要时降为短距离或情境化交互 |
| 叙事与系统脱节 | 分支只改变台词 | 所有重大叙事结果必须读取系统状态 |
| 小团队过度承诺 | 冲刺持续延期、返工增加 | 用实测产能重估，优先删内容，不透支团队 |
| 宣传造成类型误解 | 玩家期待动作爽游 | 所有素材优先展示观察、布局和后果 |

## 9. 范围削减顺序

当预算或时间不足时，按以下顺序削减：

1. 装饰性支线和低影响对白。
2. 独特路人、店面和低复用资产。
3. 摩托自由驾驶范围。
4. 次要事件数量。
5. 将一个街区合并或删除。
6. 减少结局演出差异，但保留系统状态差异。

不得优先削减：

- 核心循环清晰度。
- 非战斗解法的深度。
- NPC决策可解释性。
- 存档、性能、输入和稳定性。
- 关键无障碍功能。
- 原创化和法律合规。

## 10. 推荐的第一步执行清单

项目无需立即招聘完整团队或搭建五个街区。接下来只执行以下工作：

1. 完成一页产品提案和原创化清单。
2. 访谈 20 名目标玩家，验证定位语言。
3. 用纸面 / 简单数字原型建立瓜摊事件的事实、认知、空间和证词模型。
4. 分别测试压力对话和空间布置，不制作正式美术。
5. 达到阶段2验收标准后，再选定引擎制作灰盒原型。
6. 灰盒原型通过后，才制定垂直切片预算和人员计划。
7. 垂直切片通过前，不承诺完整五章制作。

这套顺序的目的不是延缓开发，而是尽可能早地回答最重要的问题：**玩家是否真的会因为自己观察、判断和布置了一场冲突而感到聪明、紧张，并愿意再玩一次。**
