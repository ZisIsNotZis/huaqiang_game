# 项目协作规范

## 决策原则

1. 以可玩构建和外部测试证据裁决设计争议。
2. 先验证高风险假设，再扩大内容或美术投入。
3. 不得绕过 [`docs/designs/README.md`](docs/designs/README.md) 中的阶段门。
4. 任何人不得把影视素材、演员肖像、原剧台词、截图、音乐或录音提交到项目。
5. 未经创意负责人和制作人共同批准，不得扩大当前里程碑范围。

## 分支与提交

- 主分支必须保持可检查；引擎项目建立后必须保持可构建。
- 功能分支应短生命周期，并在合并前完成评审。
- 提交格式使用 Conventional Commits：

```text
<type>: <description>
```

- 常用类型：`feat`、`fix`、`docs`、`test`、`refactor`、`build`、`chore`。
- 一个提交只处理一个完整目的，不混入无关文件。
- 大型二进制资源在引擎和资产管线确定后使用 Git LFS；在此之前不提交高分辨率源资产。

## 资产命名

引擎确定后使用：

```text
[TYPE]_[NAME]_[VARIANT]_[VERSION]
```

示例：`ENV_FruitStall_Counter_A_v003.fbx`。

命名规则在垂直切片前由技术美术和美术负责人确认，避免过早固定不适合实际工具链的细节。

## 完成定义

文档任务只有在内容已评审、交叉引用有效、未虚构审批结果且能通过项目检查脚本后完成。

未来的代码、系统和事件使用开发计划分册中的“功能完成定义”和“事件完成定义”。

## 安全与权利

- 不提交密钥、账号、个人信息、未获授权的第三方资源或受保密协议约束的资料。
- 外包资产必须保留合同、许可来源和可商用证明。
- 发现疑似侵权或秘密泄露时停止传播，隔离相关文件并通知项目负责人。
